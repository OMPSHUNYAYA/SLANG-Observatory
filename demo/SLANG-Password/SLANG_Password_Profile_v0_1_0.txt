Deterministic Admission of Declared Password-Verification Evidence

Status: Normative reference profile
Project: SLANG-Password
Version: 0.1.0
Core version: SLANG-CORE-1-D05
Profile identifier: SLANG-PASSWORD-PROFILE-1-D01
Ruleset identifier: SLANG-PASSWORD-RULESET-1-D01
Canonicalization identifier: SLANG-CANONICAL-JSON-1-D02
Verifier evidence profile: PASSWORD-VERIFIER-EVIDENCE-1

======================================================================
1. PURPOSE
======================================================================

SLANG-Password is a bounded deterministic resolver for declared
password-verification evidence.

The resolver answers this question:

Can the declared password-verification evidence be admitted under the
identified context, profile, ruleset, and evidence mode?

The central contract is:

same admitted canonical evidence + same bound context + same versioned
profile and ruleset -> same bounded result state

The resolver does not accept raw-password fields as supported input and does
not compare passwords. It receives declared evidence produced outside the
resolver and evaluates whether that evidence is:

- structurally complete;
- structurally consistent;
- bound to the declared subject reference;
- bound to the declared credential reference and credential version;
- bound to the declared request, relying party, and challenge;
- supplied by the expected verifier set;
- expressed under the supported verifier evidence profile;
- compatible with the selected evidence mode; and
- admissible under this versioned profile and ruleset.

The resolver separates four questions:

1. What verification outcome is declared by admitted evidence?
2. Is that evidence structurally admissible?
3. Is the outcome permitted to be visible in the reference presentation?
4. Does the result authorize authentication, access, session creation, or
   execution?

The answer to question 4 is always NONE under this profile.

======================================================================
2. CLAIM BOUNDARY
======================================================================

This profile defines deterministic structural admission of declared
password-verification evidence.

It does not:

- admit a raw password as supported input;
- compare a password with a stored credential;
- store or derive a password hash;
- authenticate a person, account, device, or process;
- establish identity ownership;
- grant access;
- create or validate a session;
- issue a token;
- replace password hashing, salts, peppers, key management, MFA, rate
  limiting, lockout, abuse detection, authorization, identity governance,
  endpoint security, network security, or operational monitoring;
- establish the trustworthiness of a verifier;
- establish that the declared password comparison actually occurred;
- establish source authenticity through hashing alone; or
- establish real-world truth merely because reconstruction succeeds.

The reference profile fixes these authority fields:

execution_authority = NONE
authentication_authority = NONE
access_authority = NONE
session_authority = NONE

A receipt produced by this profile is not an authentication credential, access
token, session token, password-reset token, or execution instruction.

======================================================================
3. TWO-PLANE USE MODEL
======================================================================

A conforming deployment may place SLANG-Password beside an existing security
system.

Security plane responsibilities may include:

- secret collection;
- password hashing and comparison;
- credential storage;
- MFA;
- retry and lockout policy;
- challenge expiry and consumption;
- session management;
- authorization; and
- enforcement.

SLANG structural plane responsibilities under this profile are limited to:

- strict input admission;
- canonical normalization;
- context binding;
- verifier-set checking;
- exact evidence agreement;
- deterministic state resolution;
- identity construction;
- reconstruction bundle construction;
- compact receipt construction; and
- presentation redaction according to the declared visibility flag.

A protected action may use a relation such as:

protected_action_allowed = security_checks_pass AND
                           structural_evidence_admitted AND
                           authorization_allows

SLANG-Password resolves only structural_evidence_admitted.

Supported JSON value classes are:

- object;
- array;
- string;
- integer within -(2^53 - 1) through +(2^53 - 1);

======================================================================
7. IDENTIFIER LEXICAL PROFILE AND NORMALIZATION
======================================================================

Structural identifiers use an ASCII-only lexical profile.

Before normalization, every character MUST be one of:

- horizontal tab U+0009;
- line feed U+000A;
- carriage return U+000D; or
- printable ASCII U+0020 through U+007E.

A structural identifier containing any other code point is unsupported.

Normalization MUST then:

1. remove only U+0009, U+000A, U+000D, and U+0020 from the beginning and end;
2. map only ASCII letters a-z to A-Z; and
3. validate the result against this grammar:

^[A-Z0-9][A-Z0-9._:@/-]{0,127}$

Examples:

subject-alpha -> SUBJECT-ALPHA
 verifier-a  -> VERIFIER-A
\t subject-alpha \r\n -> SUBJECT-ALPHA

The following are unsupported:

- an identifier ending in U+0085;
- an identifier ending in U+00A0;
- an identifier beginning with U+2003;
- ßprint;
- ﬁle; and
- identifiers containing fullwidth Latin letters.

This profile applies no Unicode normalization, Unicode compatibility mapping,
locale-sensitive casing, or Unicode case folding.

Unicode normalization form = NONE
Unicode case folding = NONE
non-ASCII structural identifier input = UNSUPPORTED

An identifier that does not satisfy this lexical profile or grammar produces
INVALID_IDENTIFIER and an UNSUPPORTED state unless a higher-precedence issue
applies.

======================================================================
8. COMMITMENT FORMAT
======================================================================

Each verifier evidence record MUST contain evidence_commitment.

A commitment string MUST use the permitted ASCII input character set declared
for structural identifiers. Normalization MUST remove only U+0009, U+000A,
U+000D, and U+0020 from the beginning and end, then map only ASCII letters A-Z
to a-z.

The supported normalized commitment grammar is:

sha256:[0-9a-f]{64}

The normalized prefix and hexadecimal digest MUST be lowercase. Non-ASCII
whitespace, Unicode compatibility characters, and non-ASCII hexadecimal
lookalikes are unsupported.

This profile treats evidence_commitment as a declared commitment string. The
reference resolver checks its syntax and includes it in the evidence identity.
The resolver does not independently establish what source bytes were committed,
who created the commitment, or whether the committed evidence is trustworthy.

commitment identity != source authenticity

10. FORBIDDEN SECRET AND AUTHORITY FIELDS
======================================================================

The resolver MUST NOT admit raw secret material or caller-declared authority
outcomes as supported input.

The reference implementation recursively detects these forbidden field names:

- password
- raw_password
- current_password
- old_password
- new_password
- secret
- raw_secret
- password_hash
- stored_hash
- credential_hash
- salt
- pepper
- private_key
- session_token
- access_token
- refresh_token
- authenticated
- access
- grant
- granted
- login_success
- authentication_success
- resolution_state
- verification_outcome
- admission_state
- outcome_visible
- result_id
- bundle_id
- receipt_id

The scan applies at every nesting depth. Field-name matching MUST use only
the ASCII trimming and ASCII lowercase rules declared by this profile. A
non-ASCII field name MUST NOT be Unicode-folded into a forbidden ASCII field
name. It remains subject to the exact supported-field rules and normally
produces UNKNOWN_FIELD and an UNSUPPORTED state.

The presence of any such field produces FORBIDDEN_FIELD_PRESENT and a
FORBIDDEN state.

Before reconstruction artifacts or their identities are constructed, the value
associated with each detected forbidden field is replaced with:

<FORBIDDEN_VALUE_REDACTED>

This protection operates on field names. It does not inspect or classify field
values.

A value placed in an otherwise permitted reference field, including
subject_ref, credential_ref, request_ref, relying_party_ref, or challenge_ref,
is treated as a declared reference. When valid under the identifier grammar,
that value MAY appear in the result, reconstruction bundle, and receipt.

The caller contract is:

reference field -> opaque non-secret reference only

Callers MUST NOT place passwords, tokens, private keys, hashes, personal data,
or other secret material inside reference fields. Identifier normalization and
syntax validation MUST NOT be interpreted as secret-detection mechanisms.

The resolver result declares:

secret_material_processed = false

This declaration means the supported resolution path does not use secret
material to perform a password comparison. Inputs containing recognized
forbidden fields are rejected and redacted. Preventing secret material from
being placed inside permitted fields remains the caller's responsibility.

forbidden-field rejection != content-based secret detection
identifier validation != sensitivity classification
redaction != confidentiality system

======================================================================
12. EVIDENCE MODES
======================================================================

This profile supports exactly two evidence modes.

12.1 SINGLE_VERIFIER

Requirements:

- expected_verifier_ids MUST contain exactly one unique identifier;
- verifier_evidence MUST contain exactly one record from that verifier; and
- the evidence record MUST satisfy all context and profile requirements.

12.2 MULTI_VERIFIER_EXACT_AGREEMENT

Requirements:

- expected_verifier_ids MUST contain between 2 and 8 unique identifiers;
- verifier_evidence MUST contain one record for every expected verifier;
- no unexpected verifier may be present;
- evidence_id values MUST be unique;
- verifier_id values MUST be unique; and
- every admitted verification_result MUST be identical.

This profile does not use majority voting, weighting, quorum substitution, or
first-arrival selection.

all admitted verifier outcomes agree -> continue
any admitted verifier disagreement -> CONFLICT

A MATCH outcome MUST NOT outvote a NO_MATCH outcome. A disagreement produces
EVIDENCE_RESULT_DISAGREEMENT.

The maximum number of evidence records is:

MAX_EVIDENCE_RECORDS = 8

- relying_party_ref
- challenge_ref

verifier_profile_id MUST equal:

- MATCH

MATCH means that the external verifier declares a matching password-verification

NO_MATCH means that the external verifier declares a non-matching

The reference resolver does not independently repeat that password comparison.

======================================================================
14. CONTEXT BINDING
======================================================================

Every evidence record MUST exactly match the normalized context for:

- subject_ref
- credential_ref
- credential_version
- request_ref
- relying_party_ref
- challenge_ref

A mismatch produces the corresponding conflict reason:

- SUBJECT_BINDING_MISMATCH
- CREDENTIAL_BINDING_MISMATCH
- CREDENTIAL_VERSION_MISMATCH
- REQUEST_BINDING_MISMATCH
- RELYING_PARTY_BINDING_MISMATCH
- CHALLENGE_BINDING_MISMATCH

Context binding prevents a declared result for one bounded context from being
admitted as though it applied to another bounded context.

A change to credential_version changes the context identity and result identity.
This does not by itself revoke prior operational sessions or perform credential
rotation.

15. DECLARED IDENTITIES

- declared_context_id

A missing declared identity produces MISSING_DECLARED_IDENTITY.

A malformed declared identity produces INVALID_DECLARED_IDENTITY.

A syntactically valid but unequal declared identity produces
DECLARED_IDENTITY_MISMATCH and a CONFLICT state.

The context identity prefix is:

slang_password_context_sha256:

The evidence-set identity prefix is:

slang_password_evidence_set_sha256:

Each prefix is followed by exactly 64 lowercase hexadecimal characters.

======================================================================
16. CANONICALIZATION
======================================================================

Canonical JSON is produced by:

- validating the portable JSON boundary;
- preserving supported JSON data types;
- escaping non-ASCII characters in JSON form;
- sorting object keys lexicographically;
- using no insignificant whitespace;
- using comma as the item separator;
- using colon as the key-value separator; and
- appending a single line-feed byte when writing a JSON artifact file.

The logical canonical serialization is equivalent to:

json.dumps(value,
           ensure_ascii=true,
           allow_nan=false,
           sort_keys=true,
           separators=(",", ":"))

Evidence records are normalized and then sorted by:

1. verifier_id;
2. evidence_id; and
3. canonical record serialization.

Object-key order and admitted evidence-record presentation order do not become
resolution authority.

same semantic admitted structure -> same canonical projection

======================================================================
17. STATE MODEL
======================================================================

The resolver supports these resolution states:

- RESOLVED
- INCOMPLETE
- CONFLICT
- FORBIDDEN
- UNSUPPORTED
- ABSTAIN

17.1 RESOLVED

The supported structure is complete, consistent, authorized for evaluation,
and produces one admitted verification outcome.

17.2 INCOMPLETE

Required structure or expected verifier evidence is missing.

17.3 CONFLICT

Supported declarations disagree, duplicate identities create ambiguity, a
binding differs, an unexpected verifier is present, or a declared identity does
not match its recomputed identity.

17.4 FORBIDDEN

The input contains raw secret material, caller-supplied authority outcomes, or
other forbidden fields.

17.5 UNSUPPORTED

The input uses an unknown schema, profile, ruleset, evidence mode, verifier
profile, result symbol, field, identifier form, or resource shape.

17.6 ABSTAIN

The structure is otherwise supported, but evaluation_authorized is false.

ABSTAIN is not a successful password-verification result and does not produce
MATCH or NO_MATCH.

======================================================================
18. PRECEDENCE
======================================================================

When multiple issues exist, the primary resolution state is selected by this
precedence:

FORBIDDEN > CONFLICT > UNSUPPORTED > INCOMPLETE > ABSTAIN > RESOLVED

Within the same state, the primary issue is selected by ascending reason code
and then ascending detail string.

All distinct reason codes are retained in sorted order, subject to:

MAX_REASON_CODES = 64

The result collections reason_codes, missing_dependencies, conflicts,
prohibitions, and unsupported_features are each independently deduplicated,
sorted, and capped at MAX_REASON_CODES.

INCOMPLETE deliberately outranks ABSTAIN. When evaluation_authorized is false
and a higher-precedence structural issue also exists, the higher-precedence
state remains primary and EVALUATION_NOT_AUTHORIZED remains in reason_codes.
ABSTAIN is selected only when no higher-precedence issue exists.

Precedence is part of the versioned ruleset. Check ordering MUST NOT change the
primary state for the same admitted input.

======================================================================
19. VERIFICATION OUTCOME AND ADMISSION
======================================================================

verification_outcome has these values:

- MATCH
- NO_MATCH
- NONE

admission_state has these values:

- ADMIT
- DENY
- WITHHOLD

The mapping is:

RESOLVED + MATCH -> verification_outcome = MATCH
                    admission_state = ADMIT

RESOLVED + NO_MATCH -> verification_outcome = NO_MATCH
                       admission_state = DENY

FORBIDDEN, CONFLICT, UNSUPPORTED, INCOMPLETE, or ABSTAIN ->
    verification_outcome = NONE
    admission_state = WITHHOLD

ADMIT means only that the bounded declared MATCH evidence is structurally
admitted under this profile.

DENY means only that the bounded declared NO_MATCH evidence is structurally
admitted under this profile.

Neither value grants or denies operational access by itself.

A NO_MATCH result is a resolved negative outcome. It is not a structural
conflict.

======================================================================
20. VISIBILITY
======================================================================

The result separates structural resolution from reference presentation.

visibility_state has these values:

- VISIBLE
- WITHHELD

outcome_visible is a boolean.

For a RESOLVED result:

reference_visibility_authorized = true -> VISIBLE
reference_visibility_authorized = false -> WITHHELD

The full reconstruction bundle retains the deterministic result. The public
summary exposes verification_outcome and admission_state only when
outcome_visible is true.

When the outcome is withheld, the public summary sets:

verification_outcome = null
admission_state = null
outcome_fields_redacted = true

Visibility authorization does not create authentication, access, execution, or
session authority.

26. COMMAND-LINE BEHAVIOR

Exit codes are:

1 = verification or self-test failure

does not mean that the result state was RESOLVED or that access was granted.

======================================================================
28. DETERMINISM AND ORDER INDEPENDENCE
======================================================================

Within this profile:

same admitted canonical input -> same result object
same field-name-redacted submitted input -> same reconstruction bundle
same verified bundle -> same compact receipt

The following presentation changes do not change the bounded result identity:

- top-level object-key order;
- context object-key order;
- evidence record field order; and
- verifier evidence record order, when the same unique records are present.

The following semantic changes are expected to change one or more identities:

- request_ref change;
- credential_version change;
- evidence_commitment change;
- verification_result change;
- context binding change;
- verifier-set change;
- profile or ruleset change; and
- visibility authorization change.

Order independence applies only to admitted presentation permutations of the
same bounded structure. It does not mean that arbitrary operational workflows,
network events, credential histories, or security controls are interchangeable.

======================================================================
29. PRIVACY BOUNDARY
======================================================================

The profile assumes that an untrusted caller may control the entire submitted
JSON document, including identifiers, verifier declarations, evidence
commitments, declared identities, context flags, field order, evidence order,
unknown fields, and caller-supplied conclusions.

A conforming integration SHOULD use opaque, non-secret references for:

- subject_ref;
- credential_ref;
- request_ref;
- relying_party_ref; and
- challenge_ref.

The reference example uses readable identifiers for inspectability. Those
identifiers are not a recommendation to include personal data in operational
artifacts.

The resolver does not require:

- username;
- email address;
- raw password;
- password hash;
- salt;
- pepper;
- session token; or
- access token.

Forbidden-field protection is name-based, recursive, and case-insensitive. It
is not content-based secret discovery. A caller that places secret or personal
material inside a permitted reference field violates this profile's caller
contract, and the value may be preserved in result, bundle, or receipt
artifacts.

Organizations remain responsible for data minimization, retention, access
control, authenticity mechanisms, secure transport, secure storage, legal
obligations, and secure handling of all surrounding records.

======================================================================
30. SECURITY INTERPRETATION
======================================================================

The reference result MUST be interpreted narrowly.

RESOLVED + MATCH + ADMIT means:

The declared MATCH evidence is complete and consistent under this bounded
profile and context.

It does not mean:

- the user is authenticated;
- the subject owns the account;
- the verifier is trustworthy;
- MFA passed;
- risk checks passed;
- access is authorized;
- a session should be created; or
- an action should execute.

RESOLVED + NO_MATCH + DENY means:

The declared NO_MATCH evidence is complete and consistent under this bounded
profile and context.

It does not perform account lockout, rate limiting, alerting, or recovery.

======================================================================
31. CONFORMANCE
======================================================================

A conforming implementation of this profile MUST:

- implement the strict portable JSON boundary, including the declared byte,
  depth, node, collection, string, identifier, and evidence-count limits;
- reject duplicate JSON keys;
- apply the declared ASCII-only identifier lexical profile and normalization;
- apply the declared ASCII-only commitment normalization;
- avoid Unicode normalization, compatibility mapping, and Unicode case folding
  for structural identifiers, commitments, and forbidden-field matching;
- enforce the exact supported schemas and field sets;
- reject forbidden secret and caller-derived field names recursively;
- preserve the documented distinction between field-name rejection and
  value-content classification;
- enforce context binding;
- enforce verifier-set requirements;
- enforce exact multi-verifier agreement;
- apply the declared state precedence, including INCOMPLETE over ABSTAIN;
- cap every public diagnostic collection at MAX_REASON_CODES;
- distinguish NO_MATCH from structural conflict;
- separate visibility from resolution;
- fix all authority fields to NONE;
- construct identities from the declared canonical material;
- reconstruct bundles and receipts exactly; and
- pass the frozen conformance evidence supplied for this version.

A conforming implementation MUST NOT claim that passing reconstruction proves
source authenticity, identity ownership, successful authentication, access
authority, session authority, or real-world truth.
