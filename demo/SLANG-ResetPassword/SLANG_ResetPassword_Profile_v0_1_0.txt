======================================================================
1. PURPOSE
======================================================================

SLANG-ResetPassword is a bounded deterministic resolver for declared
credential-replacement authorization evidence.

The resolver answers this question:

Can the declared reset-authorization evidence be admitted under the identified
context, authorizer set, evidence mode, profile, and ruleset?

The central contract is:

same admitted canonical evidence + same bound reset context + same versioned
profile and ruleset -> same bounded result state

The resolver does not accept passwords, reset tokens, one-time passwords,
recovery codes, or other recovery secrets as supported input. It does not
validate those secrets and does not replace a credential. It receives declared
authorization evidence produced outside the resolver and evaluates whether that
evidence is:

- structurally complete;
- structurally consistent;
- bound to the declared subject reference;
- bound to the declared credential reference and pre-replacement version;
- bound to the declared replacement request, relying party, and recovery case;
- supplied by the expected authorizer set;
- expressed under the supported authorization evidence profile;
- compatible with the selected evidence mode; and
- admissible under this versioned profile and ruleset.

The resolver separates four questions:

1. What reset-authorization outcome is declared by admitted evidence?
2. Is that evidence structurally admissible?
3. Is the outcome permitted to be visible in the reference presentation?
4. Does the result authorize credential mutation, reset execution,
   authentication, access, session creation, or other execution?

The answer to question 4 is always NONE under this profile.

======================================================================
2. CLAIM BOUNDARY
======================================================================

This profile defines deterministic structural admission of declared
credential-replacement authorization evidence.

It does not:

- admit a current password, new password, reset token, one-time password,
  recovery code, backup code, or other recovery secret as supported input;
- validate a recovery token, one-time password, recovery code, or identity
  proofing event;
- compare passwords or derive password strength;
- generate, store, replace, rotate, disable, or delete a credential;
- authenticate a person, account, device, or process;
- establish identity ownership;
- grant access;
- create or validate a session;
- issue or consume a token;
- replace password hashing, credential storage, MFA, recovery controls, expiry,
  replay prevention, rate limiting, lockout, abuse detection, authorization,
  identity governance, endpoint security, network security, or operational
  monitoring;
- establish the trustworthiness or independence of an authorizer;
- establish that the declared recovery checks actually occurred;
- establish source authenticity through hashing alone; or
- establish real-world truth merely because reconstruction succeeds.

The reference profile fixes these authority fields:

execution_authority = NONE
reset_authority = NONE
credential_mutation_authority = NONE
authentication_authority = NONE
access_authority = NONE
session_authority = NONE

A receipt produced by this profile is not a reset token, credential-mutation
instruction, authentication credential, access token, session token, or
execution instruction.

3. TWO-PLANE USE MODEL
======================================================================

A conforming deployment may place SLANG-ResetPassword beside an existing
credential-recovery and security system.

Security-plane responsibilities may include:

- account discovery and recovery-channel selection;
- identity proofing;
- reset-token, one-time-password, or recovery-code generation and validation;
- expiry, replay prevention, challenge consumption, and retry controls;
- password-policy and breach checks;
- credential hashing, storage, replacement, rotation, and revocation;
- MFA and step-up authentication;
- session invalidation and account-protection policy;
- abuse detection, rate limiting, lockout, notification, and monitoring;
- authorization; and
- enforcement.

SLANG structural-plane responsibilities under this profile are limited to:

- strict input admission;
- canonical normalization;
- reset-context binding;
- authorizer-set checking;
- exact evidence agreement;
- deterministic state resolution;
- identity construction;
- reconstruction bundle construction;
- compact receipt construction; and
- presentation redaction according to the declared visibility flag.

A surrounding system may use a relation such as:

credential_replacement_may_proceed = recovery_checks_pass AND
                                     structural_reset_authorization_admitted AND
                                     operational_policy_allows

SLANG-ResetPassword resolves only structural_reset_authorization_admitted.

6. PORTABLE JSON BOUNDARY
======================================================================

The reference input is strict UTF-8 JSON.

The parser MUST reject:

- duplicate object keys;
- malformed JSON;
- non-UTF-8 input;
- floating-point numbers;
- NaN;
- positive or negative Infinity;
- integers outside the portable safe range;
- lone Unicode surrogate code points;
- values outside the supported JSON type boundary; and
- inputs exceeding declared resource limits.

Supported JSON value classes are:

- object;
- array;
- string;
- integer within -(2^53 - 1) through +(2^53 - 1);
- boolean; and
- null.

Floating-point values are not supported by this profile.

The maximum UTF-8 JSON input size is:

MAX_JSON_INPUT_BYTES = 1048576

MAX_JSON_INPUT_BYTES applies to the original UTF-8 source bytes accepted
through loads_strict, load_json, and command-line file input.

Every submitted input is also checked against MAX_JSON_INPUT_BYTES using the
UTF-8 byte length of its canonical JSON serialization. This canonical-size
measure applies to already constructed Python objects passed directly to
resolve_reset_password(value), normalized_projection(value), or
build_bundle(value), and also applies after parsing serialized input.

The source-byte measure and canonical-size measure are deterministic but are
not defined as equivalent at the exact limit. Canonical serialization removes
insignificant whitespace and escapes non-ASCII characters.

The submitted-input ceiling does not apply to the complete reconstruction
bundle, compact receipt, public summary, or their verification paths. A valid
artifact may serialize larger than its submitted input.

The maximum structural depth is:

MAX_JSON_DEPTH = 48

The maximum total node count is:

MAX_JSON_NODES = 50000

The maximum object member count and general array length are:

MAX_LIST_LENGTH = 256

The maximum string length is:

MAX_STRING_LENGTH = 1024

The maximum object-key length and identifier length are:

MAX_IDENTIFIER_LENGTH = 128

7. IDENTIFIER LEXICAL PROFILE AND NORMALIZATION
======================================================================

Structural identifiers use an ASCII-only lexical profile.

Before normalization, every character MUST be one of:

- horizontal tab U+0009;
- line feed U+000A;
- carriage return U+000D; or
- printable ASCII U+0020 through U+007E.

A structural identifier containing any other code point is unsupported.

Normalization MUST then:

1. remove only U+0009, U+000A, U+000D, and U+0020 from the beginning and end;
2. map only ASCII letters a-z to A-Z; and
3. validate the result against this grammar:

^[A-Z0-9][A-Z0-9._:@/-]{0,127}$

Examples:

subject-alpha -> SUBJECT-ALPHA
 authorizer-a  -> AUTHORIZER-A
\t subject-alpha \r\n -> SUBJECT-ALPHA

The following are unsupported:

- an identifier ending in U+0085;
- an identifier ending in U+00A0;
- an identifier beginning with U+2003;
- ßprint;
- ﬁle; and
- identifiers containing fullwidth Latin letters.

This profile applies no Unicode normalization, Unicode compatibility mapping,
locale-sensitive casing, or Unicode case folding.

Unicode normalization form = NONE
Unicode case folding = NONE
non-ASCII structural identifier input = UNSUPPORTED

An identifier that does not satisfy this lexical profile or grammar produces
INVALID_IDENTIFIER and an UNSUPPORTED state unless a higher-precedence issue
applies.

======================================================================
8. COMMITMENT FORMAT
======================================================================

Each authorization evidence record MUST contain evidence_commitment.

A commitment string MUST use the permitted ASCII input character set declared
for structural identifiers. Normalization MUST remove only U+0009, U+000A,
U+000D, and U+0020 from the beginning and end, then map only ASCII letters A-Z
to a-z.

The supported normalized commitment grammar is:

sha256:[0-9a-f]{64}

The normalized prefix and hexadecimal digest MUST be lowercase. Non-ASCII
whitespace, Unicode compatibility characters, and non-ASCII hexadecimal
lookalikes are unsupported.

This profile treats evidence_commitment as a declared commitment string. The
reference resolver checks its syntax and includes it in the evidence identity.
The resolver does not independently establish what source bytes were committed,
who created the commitment, or whether the committed evidence is trustworthy.

commitment identity != source authenticity

======================================================================
12. EVIDENCE MODES
======================================================================

This profile supports exactly two evidence modes.

12.1 SINGLE_AUTHORIZER

Requirements:

- expected_authorizer_ids MUST contain exactly one unique identifier;
- authorization_evidence MUST contain exactly one record from that authorizer; and
- the evidence record MUST satisfy all context and profile requirements.

12.2 MULTI_AUTHORIZER_EXACT_AGREEMENT

Requirements:

- expected_authorizer_ids MUST contain between 2 and 8 unique identifiers;
- authorization_evidence MUST contain one record for every expected authorizer;
- no unexpected authorizer may be present;
- evidence_id values MUST be unique;
- authorizer_id values MUST be unique; and
- every admitted authorization_result MUST be identical.

This profile does not use majority voting, weighting, quorum substitution, or
first-arrival selection.

all admitted authorizer outcomes agree -> continue
any admitted authorizer disagreement -> CONFLICT

A RESET_AUTHORIZED outcome MUST NOT outvote a RESET_NOT_AUTHORIZED outcome. A disagreement produces
EVIDENCE_RESULT_DISAGREEMENT.

The maximum number of evidence records is:

MAX_EVIDENCE_RECORDS = 8

16. CANONICALIZATION
======================================================================

Canonical JSON is produced by:

- validating the portable JSON boundary;
- preserving supported JSON data types;
- escaping non-ASCII characters in JSON form;
- sorting object keys lexicographically;
- using no insignificant whitespace;
- using comma as the item separator;
- using colon as the key-value separator; and
- appending a single line-feed byte when writing a JSON artifact file.

The logical canonical serialization is equivalent to:

json.dumps(value,
           ensure_ascii=true,
           allow_nan=false,
           sort_keys=true,
           separators=(",", ":"))

Evidence records are normalized and then sorted by:

1. authorizer_id;
2. evidence_id; and
3. canonical record serialization.

Object-key order and admitted evidence-record presentation order do not become
resolution authority.

same semantic admitted structure -> same canonical projection

======================================================================
17. STATE MODEL
======================================================================

The resolver supports these resolution states:

- RESOLVED
- INCOMPLETE
- CONFLICT
- FORBIDDEN
- UNSUPPORTED
- ABSTAIN

17.1 RESOLVED

The supported structure is complete, consistent, authorized for evaluation,
and produces one admitted authorization outcome.

17.2 INCOMPLETE

Required structure or expected authorization evidence is missing.

17.3 CONFLICT

Supported declarations disagree, duplicate identities create ambiguity, a
binding differs, an unexpected authorizer is present, or a declared identity does
not match its recomputed identity.

17.4 FORBIDDEN

The input contains raw secret material, caller-supplied authority outcomes, or
other forbidden fields.

17.5 UNSUPPORTED

The input uses an unknown schema, profile, ruleset, evidence mode, authorizer
profile, result symbol, field, identifier form, or resource shape.

17.6 ABSTAIN

The structure is otherwise supported, but evaluation_authorized is false.

ABSTAIN is not a successful reset-authorization result and does not produce
RESET_AUTHORIZED or RESET_NOT_AUTHORIZED.

======================================================================
18. PRECEDENCE
======================================================================

When multiple issues exist, the primary resolution state is selected by this
precedence:

FORBIDDEN > CONFLICT > UNSUPPORTED > INCOMPLETE > ABSTAIN > RESOLVED

Within the same state, the primary issue is selected by ascending reason code
and then ascending detail string.

All distinct reason codes are retained in sorted order, subject to:

MAX_REASON_CODES = 64

The result collections reason_codes, missing_dependencies, conflicts,
prohibitions, and unsupported_features are each independently deduplicated,
sorted, and capped at MAX_REASON_CODES.

INCOMPLETE deliberately outranks ABSTAIN. When evaluation_authorized is false
and a higher-precedence structural issue also exists, the higher-precedence
state remains primary and EVALUATION_NOT_AUTHORIZED remains in reason_codes.
ABSTAIN is selected only when no higher-precedence issue exists.

Precedence is part of the versioned ruleset. Check ordering MUST NOT change the
primary state for the same admitted input.

======================================================================
19. AUTHORIZATION OUTCOME AND ADMISSION
======================================================================

authorization_outcome has these values:

- RESET_AUTHORIZED
- RESET_NOT_AUTHORIZED
- NONE

admission_state has these values:

- ADMIT
- DENY
- WITHHOLD

The mapping is:

RESOLVED + RESET_AUTHORIZED -> authorization_outcome = RESET_AUTHORIZED
                    admission_state = ADMIT

RESOLVED + RESET_NOT_AUTHORIZED -> authorization_outcome = RESET_NOT_AUTHORIZED
                       admission_state = DENY

FORBIDDEN, CONFLICT, UNSUPPORTED, INCOMPLETE, or ABSTAIN ->
    authorization_outcome = NONE
    admission_state = WITHHOLD

ADMIT means only that the bounded declared RESET_AUTHORIZED authorization evidence is structurally
admitted under this profile.

DENY means only that the bounded declared RESET_NOT_AUTHORIZED authorization evidence is structurally
admitted under this profile.

Neither value grants or denies operational access by itself.

A RESET_NOT_AUTHORIZED result is a resolved negative outcome. It is not a structural
conflict.

======================================================================
20. VISIBILITY
======================================================================

The result separates structural resolution from reference presentation.

visibility_state has these values:

- VISIBLE
- WITHHELD

outcome_visible is a boolean.

For a RESOLVED result:

reference_visibility_authorized = true -> VISIBLE
reference_visibility_authorized = false -> WITHHELD

The full reconstruction bundle and compact receipt retain the deterministic
result regardless of visibility_state. They are verification artifacts, not
visibility-filtered presentation surfaces.

Visibility filtering is applied only by the public summary.

When a RESOLVED outcome is withheld, the public summary MUST set:

authorization_outcome = null
admission_state = null
reason_codes = [RESET_OUTCOME_WITHHELD]
result_id = null
bundle_id = null
outcome_fields_redacted = true

The public summary MUST NOT expose an outcome-revealing reason code or an
outcome-dependent private result or bundle identity when outcome_visible is
false.

For otherwise identical withheld cases, changing only RESET_AUTHORIZED to
RESET_NOT_AUTHORIZED MUST NOT change the public summary or public_summary_id.
This property is WITHHELD_OUTCOME_NONINTERFERENCE.

Visibility authorization does not create reset, credential-mutation,
authentication, access, execution, or session authority.

23. RECONSTRUCTION BUNDLE

- version

- canonicalization_id

Bundle verification MUST:

1. validate portable JSON;
2. require the exact bundle field set;
3. verify schema, version, core version, canonicalization, and identity domain;
4. reconstruct normalized_projection and result from submitted_input;
5. reconstruct bundle_id; and
6. require canonical equality with the supplied bundle.

A passing bundle verification demonstrates deterministic reconstruction under
this implementation and versioned profile. It does not establish source
authenticity, operational reset authorization, or credential-mutation authority.

======================================================================

The receipt schema is:

SLANG-RESET-PASSWORD-RECEIPT-1

The receipt contains selected bounded result fields and binds them to bundle_id.
It does not reproduce submitted_input or values under unknown or unsupported
fields.

The receipt retains authorization_outcome, admission_state, reason_codes,
result_id, and bundle_id even when visibility_state = WITHHELD. It is not
visibility-filtered and MUST be treated as a sensitive, access-controlled
verification artifact. It MUST NOT be used as the public presentation surface
for a withheld outcome.

Compactness does not establish that a receipt is non-sensitive.

It includes:

- schema and version fields;
- context references;
- state and visibility fields;
- all principal identity fields;
- reason codes;
- fixed authority fields;
- source_authenticity;
- bundle_id; and
- receipt_id.

Receipt verification MUST:

1. validate portable JSON;
2. require the exact receipt field set;
3. verify schema, version, core version, canonicalization, and identity domain;
4. reconstruct receipt_id;
5. require execution_authority = NONE;
6. require reset_authority = NONE;
7. require credential_mutation_authority = NONE;
8. require authentication_authority = NONE;
9. require access_authority = NONE; and
10. require session_authority = NONE.

Receipt-against-bundle verification MUST reconstruct the expected receipt from
the verified bundle and require exact canonical equality.

receipt verification != source authentication
receipt verification != reset authorization or credential mutation
receipt verification != session authority
receipt verification != credential-mutation authority

======================================================================
25. PUBLIC SUMMARY
======================================================================

The public summary schema is:

SLANG-RESET-PASSWORD-PUBLIC-SUMMARY-1

The public summary is the sole visibility-aware presentation projection in this
profile.

It contains exactly:

- summary_schema
- version
- state
- resolution_state
- visibility_state
- outcome_visible
- outcome_fields_redacted
- authorization_outcome
- admission_state
- reason_codes
- execution_authority
- reset_authority
- credential_mutation_authority
- authentication_authority
- access_authority
- session_authority
- result_id
- bundle_id
- public_summary_id

When outcome_visible is true, the public summary retains the visible outcome,
admission state, outcome reason code, result_id, and bundle_id.

When outcome_visible is false, the public summary MUST:

- set authorization_outcome to null;
- set admission_state to null;
- replace a RESOLVED directional reason code with RESET_OUTCOME_WITHHELD;
- set result_id to null;
- set bundle_id to null;
- set outcome_fields_redacted to true; and
- preserve all authority fields as NONE.

public_summary_id is constructed from the complete visibility-filtered public
summary excluding public_summary_id itself, using this prefix:

slang_reset_password_public_summary_sha256:

For otherwise identical withheld RESET_AUTHORIZED and RESET_NOT_AUTHORIZED
cases, the complete public summary and public_summary_id MUST be identical.

Public-summary verification MUST enforce the exact field set, schema, version,
visibility invariants, reason-code invariants, authority boundaries, and
public_summary_id reconstruction.

Public-summary-against-bundle verification reconstructs the expected public
projection from a verified bundle and requires exact canonical equality.
Because withheld outcomes intentionally produce the same public projection,
this comparison demonstrates projection consistency, not unique public binding
to one outcome-bearing private bundle.

public-summary integrity != exact private-bundle binding
public-summary redaction != cryptographic confidentiality

The public summary is not a reset token, credential-mutation instruction,
authentication credential, access token, session authority, reconstruction
bundle, or compact receipt.

--self-test

Without --input, the script evaluates its built-in reference input.

Exit codes are:

0 = command completed successfully
1 = self-test or artifact-verification failure
2 = input, JSON boundary, I/O, or command-resolution error
3 = --require-visible-result was used and the public summary did not contain a
    visible resolved outcome

Exit code 0 for ordinary input resolution means that the command executed. It
does not mean that the result state was RESOLVED or that access was granted.

======================================================================
28. DETERMINISM AND ORDER INDEPENDENCE
======================================================================

Within this profile:

same admitted canonical input -> same result object
same field-name-redacted submitted input -> same reconstruction bundle
same verified bundle -> same compact receipt
same visibility-filtered projection -> same public summary and public_summary_id

The following presentation changes do not change the bounded result identity:

- top-level object-key order;
- context object-key order;
- evidence record field order; and
- authorization evidence record order, when the same unique records are present.

The following semantic changes are expected to change one or more identities:

- replacement_request_ref change;
- credential_version_before change;
- evidence_commitment change;
- authorization_result change;
- context binding change;
- authorizer-set change;
- profile or ruleset change; and
- visibility authorization change.

Order independence applies only to admitted presentation permutations of the
same bounded structure. It does not mean that arbitrary operational workflows,
network events, credential histories, or security controls are interchangeable.

======================================================================
29. PRIVACY BOUNDARY
======================================================================

The profile assumes that an untrusted caller may control the entire submitted
JSON document, including identifiers, authorizer declarations, evidence
commitments, declared identities, context flags, field order, evidence order,
unknown fields, and caller-supplied conclusions.

A conforming integration SHOULD use opaque, non-secret references for:

- subject_ref;
- credential_ref;
- replacement_request_ref;
- relying_party_ref; and
- recovery_case_ref.

The reference example uses readable identifiers for inspectability. Those
identifiers are not a recommendation to include personal data in operational
artifacts.

The resolver does not require:

- username;
- email address;
- current or new password;
- password hash;
- reset token;
- one-time password;
- recovery or backup code;
- salt;
- pepper;
- session token; or
- access token.

Forbidden-field protection is name-based, recursive, and ASCII
case-insensitive. It is not content-based secret discovery. A caller that
places secret or personal material inside a permitted reference field violates
this profile's caller contract, and the value may be preserved in result,
bundle, or receipt artifacts.

A value under an unknown or unsupported field name is not redacted unless that
name is also in the declared forbidden-name set. The value is retained in
submitted_input inside the reconstruction bundle even when the input resolves
to UNSUPPORTED. It is not reproduced inside the compact receipt, although the
receipt binds the corresponding submission and bundle through submission_id
and bundle_id.

Value-level secret detection is outside this profile. Redaction is keyed only
on recognized forbidden field names. A sensitive value placed inside a
permitted, unknown, or unsupported field may be retained in private artifacts.

The reconstruction bundle and compact receipt retain the full deterministic
outcome even when visibility_state = WITHHELD. Only the public summary applies
visibility filtering. Private artifacts MUST be handled within an independently
authorized verification or audit boundary.

unsupported field != redacted field
input rejected != submitted value discarded

Organizations remain responsible for data minimization, retention, access
control, authenticity mechanisms, secure transport, secure storage, legal
obligations, and secure handling of all surrounding records.

======================================================================
30. SECURITY INTERPRETATION
======================================================================

The reference result MUST be interpreted narrowly.

RESOLVED + RESET_AUTHORIZED + ADMIT means:

The declared RESET_AUTHORIZED authorization evidence is complete, consistent,
and structurally admitted under this bounded profile and reset context.

It does not mean:

- the user is authenticated;
- the subject owns the account;
- the authorizer is trustworthy;
- identity proofing, token validation, MFA, or recovery checks actually passed;
- the recovery case is current or unreplayed;
- credential replacement is authorized operationally;
- a credential should be mutated;
- access is authorized;
- a session should be created; or
- an action should execute.

RESOLVED + RESET_NOT_AUTHORIZED + DENY means:

The declared RESET_NOT_AUTHORIZED authorization evidence is complete and
consistent under this bounded profile and reset context.

It does not perform lockout, rate limiting, alerting, credential mutation, or
operational recovery handling.

======================================================================
31. CONFORMANCE
======================================================================

A conforming implementation of this profile MUST:

- implement the strict portable JSON boundary, including the declared byte,
  depth, node, collection, string, identifier, and evidence-count limits;
- reject duplicate JSON keys;
- apply the declared ASCII-only identifier lexical profile and normalization;
- apply the declared ASCII-only commitment normalization;
- avoid Unicode normalization, compatibility mapping, and Unicode case folding
  for structural identifiers, commitments, and forbidden-field matching;
- enforce the exact supported schemas and field sets;
- reject forbidden secret and caller-derived field names recursively;
- preserve the documented distinction between field-name rejection and
  value-content classification;
- enforce context binding;
- enforce authorizer-set requirements;
- enforce exact multi-authorizer agreement;
- apply the declared state precedence, including INCOMPLETE over ABSTAIN;
- cap every public diagnostic collection at MAX_REASON_CODES;
- distinguish RESET_NOT_AUTHORIZED from structural conflict;
- separate visibility from resolution;
- apply visibility filtering only through the public summary;
- neutralize outcome-revealing reason codes and private identities when a
  public outcome is withheld;
- satisfy WITHHELD_OUTCOME_NONINTERFERENCE;
- enforce the canonical-size ceiling for direct-object submitted input before
  bundle cloning;
- fix all authority fields to NONE;
- construct identities from the declared canonical material;
- reconstruct bundles, receipts, and public summaries exactly; and
- pass the frozen conformance evidence supplied for this version.

A conforming implementation MUST NOT claim that passing reconstruction proves
source authenticity, identity ownership, successful recovery checks, reset
authority, credential-mutation authority, authentication, access authority,
session authority, or real-world truth.
